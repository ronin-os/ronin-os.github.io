RōninOS Auf dem Weg zu einem unabhängigen, sicheren Open-Source-Betriebssystem 🛡️

RōninOS ist ein freestanding x86-Kernel, entwickelt als Grundstein für ein vollständig unabhängiges, quelloffenes Betriebssystem. Das Projekt verfolgt einen Security-by-Design-Ansatz: Speicherisolierung, Verschlüsselung und transparente Auditierbarkeit werden nicht als optionale Erweiterungen, sondern als architektonische Kernanforderungen behandelt. Die aktuelle Codebasis umfasst Speicherverwaltung (PMM, Paging, Heap), präemptives Scheduling, VFS mit RAMFS und FAT32 sowie einen modernen Netzwerk-Stack (lwIP) – vollständig in C, kompilierbar via Docker-Cross-Toolchain oder nativem x86_64-elf-GCC.

Unsere Vision 🎯

Ein Betriebssystem, das Sicherheit und Souveränität nicht als Option, sondern als architektonisches Fundament betrachtet.

🔓

100 % Open Source

Der vollständige Quellcode ist öffentlich einsehbar und auditierbar. Keine proprietären Binary-Blobs, keine versteckten Telemetrie-Komponenten – vollständige Transparenz von der Bootsequenz bis zur Anwendungsebene.

🔒

Security by Design

Sicherheit wird nicht als nachträgliches Feature implementiert, sondern ist integraler Bestandteil der Systemarchitektur. Speicherisolierung, gehärtete Userspace-Prozesse und minimales Privilegien-Modell bilden das Fundament.

🔑

Verschlüsselung als Standard

Full-Disk-Encryption auf Block-Ebene, signierte Update-Ketten und Ende-zu-Ende-verschlüsselte Kommunikation. Der Benutzer behält die alleinige Kontrolle über seine Daten – der OS-Hersteller hat standardmäßig keinen Zugriff.

🌍

Unabhängig & Souverän

Keine Abhängigkeit von Konzernen, keine Telemetrie-Infrastruktur, kein Vendor-Lock-in. RōninOS läuft vollständig autark auf der Hardware des Benutzers – ohne externe Zugriffe oder verpflichtende Cloud-Dienste.

Kernkomponenten 🧱

Neun modulare Subsysteme, die das technische Fundament des Kernels bilden – von der Speicherverwaltung bis zur Dateisystemabstraktion.

01

Physical Memory Manager

Bitmap-basierte 4-KiB-Frame-Verwaltung auf Basis der Multiboot2-Memory-Map. Reservierung von Low-Memory, Kernel-Image, Bootmodulen und Framebuffer. Unterstützt bis zu 512 MiB physikalischen Adressraum.

02

Paging & Heap

32-Bit-Paging mit Identity-Mapping und dynamisch allokierten Page Tables. Virtueller Heap bei 0x18000000 mit First-Fit-Freiliste, Split/Merge-Mechanik und Spinlock-basierter Synchronisation. Automatische Expansion über den PMM.

03

Thread-Scheduler

Kooperatives Round-Robin-Scheduling mit optionalem PIT-basiertem Preempting bei 100 Hz. Jeder Thread besitzt einen eigenen kmallozierten Stack sowie eine Zustandsmaschine (RUNNABLE, SLEEP, ZOMBIE). Introspektion über ps und procmon.

04

VFS & Dateisysteme

Einheitliche Virtual-Filesystem-Schnittstelle mit Path-Resolver, Working-Directory und open/read/write-API. RAMFS als Root-Dateisystem (/), Multiboot2-Module read-only unter /initrd. FAT32-Implementierung auf generischem Blockdevice-Layer.

05

Framebuffer-Konsole

Dynamisch berechnetes Raster aus Bildschirmauflösung und Font-Zellgröße. ANSI-Farben in VS-Code-Dark-Palette, Standard-Font 8x16, optional 16x32. Diagnose-Overlay für Framebuffer-Parameter aktivierbar über DEBUG=1.

06

Shell & App-System

Eigener Kommandozeilen-Parser mit Unterstützung für Builtins und registrierbare Applikationen. Die App-Registry in apps.c ermöglicht die Integration neuer Shell-Programme über die Funktion app_<name>_main() und einen Tabelleneintrag.

07

Exception-Diagnose & Debugging

Register-Dumps bei Kernel-Panics und User-Faults inklusive vollständiger CPU-Registeranzeige (EIP, CS, EFLAGS). Automatische Kernel/User-Mode-Erkennung über das CS-Segment. Manuelle Exception-Reproduktion via test_fault <gp|pf|ud>.

08

UEFI & BIOS Boot

Multiboot2-konformer ELF-Kernel-Header. Build-Targets für BIOS-ISO (GRUB-mkrescue), UEFI-Superfloppy-FAT32 sowie partitionierte MBR/FAT32-USB-Images. GRUB-Konfiguration mit mehrstufiger gfxmode-Fallbackkette und videoinfo-Debug-Eintrag.

09

Block-Devices & FAT32

ATA-PIO-basierte Block-Device-Discovery über Primary/Secondary-Bus und Master/Slave-Kanäle. Generischer Blockdevice-Layer als Abstraktionsschnittstelle. Eigene FAT32-Implementierung mit Formatieren, Mounten, Lesen, Schreiben und Löschen im 8.3-Namensraum.

10

Netzwerk-Stack (lwIP)

Integrierter lwIP 2.1.3 TCP/IP-Stack mit Unterstützung für Intel e1000 und RTL8139 Treiber. Bietet DHCP, DNS und eine Socket-API für Userspace-Anwendungen wie ping.

Systemarchitektur

Vollständiger Boot- und Initialisierungsablauf – von der Systemfirmware bis zur betriebsbereiten Shell. Der Kernel ist vollständig freestanding implementiert und weist keinerlei Abhängigkeiten von einer C-Standardbibliothek auf.

Dateisysteme

Zwei Dateisystemimplementierungen unter einem einheitlichen VFS-Layer mit Path-Resolver, Working-Directory und offener Dateiverwaltung.

RAMFS In-Memory

In-Memory-Dateisystem, vollständig im Heap allokiert. Operiert mit einer einfach verketteten Liste (O(n) für die meisten Operationen). Unterstützt touch, write, append, cat, cp, mv und rm für schnelle Dateiexperimente ohne Blockdevice.

fs touch test.txt
fs write test.txt "Hello RoninOS"
fs cat test.txt
fs rm test.txt

FAT32 Block Device

Eigene FAT32-Implementierung auf dem generischen Blockdevice-Layer (ATA PIO). Bootsektor, FSInfo, FAT und Root-Cluster werden bei format angelegt. 8.3-Dateinamen, Einzel-Cluster-Dateien (512 B).

fat32 format hd0 --yes
fat32 write NOTE.TXT "Hallo"
fat32 cat NOTE.TXT
fat32 rm NOTE.TXT

VFS + Initrd Virtuell

Einheitliche open/read/write/readdir-Schnittstelle. RAMFS als Root (/), Multiboot2-Module read-only unter /initrd. cwd pro Shell-Prozess.

ls /
cd /initrd
cat /initrd/banner.txt

Build & Run

RōninOS lässt sich via Docker (empfohlen) oder nativ mit x86_64-elf-Cross-Toolchain bauen.

1

Repository klonen

git clone https://github.com/MachuraHarry/RoninOS.git
cd RoninOS
2

BIOS-Build (ISO)

make clean && make
make verify
3

In QEMU starten

make run
make run-serial   # mit COM1-Diagnose
4

UEFI-Image + Test

make uefi-image
make uefi-run
5

Docker-Build (reproduzierbar)

scripts/build.sh
